## 为什么挑这个靶子

想认真练一遍接口测试，最头疼的是**没有稳定的被测对象**：自己写的玩具项目没有真实的业务约束，测出来的东西说服力有限；公司的系统又带不走。

最后选了 [macrozheng/mall](https://github.com/macrozheng/mall) —— 一个 Star 数很高的开源电商系统。理由很实际：它接口齐全、有真实的数据库约束和鉴权链路、能本地用 Docker 起起来，而且**别人也在用它**，说明它的行为足够真实。

> 先把归属说清楚：**mall 的作者不是我**，本仓库只有测试代码和测试文档，不含它的任何源码和资产。我在这件事里的身份只有一个——测试方。

## 先搞清楚被测对象的脾气

动手写用例之前，我先把品牌模块 `PmsBrandController` 的 9 个接口（外加登录鉴权接口作前置）逐个用 Postman 敲了一遍。这一步的目的不是"验证"，而是**先摸清这套系统的判错方式**。

摸出来的结论直接决定了后面所有断言怎么写：

| 情况 | HTTP 状态码 | 响应体 `code` |
|---|---|---|
| 成功 | **200** | 200 |
| 参数校验失败 | **200** | 404 |
| 鉴权失败 | **200** | 401 |
| 服务端异常 | **200** | 500 |

**这套系统的 HTTP 状态码恒为 200。** 业务成败完全藏在响应体的 `code` 里。

如果不知道这一点，测试代码很自然会写成「HTTP 200 就算过」——那这个项目里的 8 个缺陷，一大半都会被放过去。

## 用例怎么设计

36 条用例（设计 42 条，落地 36 条，剩 6 条待实测），按执行价值分了四层：

| 层级 | 数量 | 覆盖什么 |
|---|---|---|
| 冒烟 | — | 登录 / 增 / 查 / 改 / 删主链路，改完代码先跑这一层 |
| P0 核心回归 | 9 | 模块主干功能，每次必跑 |
| P1 校验类 | 20 | 必填、边界、类型、长度、枚举约束 |
| P2 异常语义 | 7 | 不存在的 id、越权、错误语义是否合理 |

设计方法用的是最常规那几样：等价类、边界值、枚举约束、异常语义、场景法、错误推测。真正费心思的不是"想到这些方法"，而是**对这套系统的业务约束做功课**——比如 `showStatus` 这个字段到底允许哪几个值？数据库列多长？这些决定了边界值往哪儿取。

### 断言做三层，不做一层

这是我在这个项目里学得最值钱的一条：

```
第 ① 层  网络层：HTTP 状态码
第 ② 层  业务层：响应体 code
第 ③ 层  数据层：回查落库值 / 返回结构 / 字段匹配
```

为什么要分三层？**因为只判 `code == 200` 会造成假成功。**

举个真实的例子：新增品牌接口只返回「影响行数」，不返回主键 id。如果只断言 `code == 200`，你以为加进去了；但如果字段被静默截断、或者写进了别的记录，这条用例照样"通过"。所以链式用例必须**靠关键字回查**去把刚建的数据捞出来，确认它真的按你给的值落库了。

分层还有个附带好处：用例失败时，看一眼卡在哪一层就知道问题性质——网络层失败是环境或服务挂了，业务层失败是逻辑或校验问题，数据层失败才是真正的数据一致性缺陷。

### 数据隔离

用例之间互相污染是自动化测试最烦人的问题之一。做法很简单但必须做：**用时间戳或随机后缀生成唯一的品牌名**，让每条用例操作自己的数据，不依赖也不破坏别人的前置状态。

## 三个最值得说的缺陷

一共提了 8 个缺陷（高 1 / 中 4 / 低 3），挑三个说说。

### F4（高）：「品牌名」没有长度上限，超长直接 500

传一个超长字符串当品牌名，接口直接返回 `HTTP 500`，并且**把数据库堆栈回显了出来**：

```
MysqlDataTruncation: Data truncation: Data too long for column 'name'
```

这是一个典型的**分层失守**：

- 接口层：没有 `@Size` 之类的长度校验，直接放行；
- 数据库层：列有长度上限，最后报错；
- 兜底：异常没有被转成友好的业务错误码，原始堆栈直接吐给了调用方。

危害有两个层面：功能上，用户输入超长就得吃 500；安全上，**堆栈回显等于免费给攻击者递了一份内部结构说明书**——表名、列名、技术栈全在里面。

正确的做法是把校验放在接口层，让它在进数据库之前就返回明确的业务错误。

### F8（中）：同一个字段，批量接口和单条接口的行为不一致

`showStatus`（上架状态）是个枚举字段，只允许 `0` 和 `1`。测试发现两个接口对同一个非法值的处理完全不同：

| 接口 | 传 `showStatus = 2` | 结果 |
|---|---|---|
| 单条更新 | `code 404`，被拦下 | ✅ 符合预期 |
| 批量更新 | `code 200`，**真的写进库了** | ❌ 约束被绕过 |

这类缺陷的价值在于它揭示的不是"少了一行校验"，而是**同一个校验规则在代码里有两份实现，改的时候只改了一处**。对有经验的团队来说，这往往意味着更大的维护隐患。

### F3（中）：分不清「不存在」和「成功但为空」

查询一个不存在的品牌，接口返回：

```json
{ "code": 200, "data": null }
```

`code 200` 意味着成功，但 `data` 是 `null`。调用方根本没有办法区分这两种情况：

- 查询成功，但这个品牌确实不存在；
- 查询失败，只是错误被吞掉了。

对前端来说，这会导致它必须用「猜测」的方式处理空数据；对测试来说，这意味着**语义层面的可断言性缺失**——你没法写一条干净的用例去表达"这个品牌不该存在"。

## 压测：50 并发下这个模块是什么水平

用 JMeter 非 GUI 模式压了登录 + 品牌列表两个接口：

```
50 并发（ramp-up 30s）× 10 循环
```

| 指标 | 结果 |
|---|---|
| 样本数 | 1020 |
| 错误率 | **0.00%** |
| 总吞吐 | 33.8 req/s |
| 登录平均响应 | 79 ms |
| 品牌列表平均响应 | 8.0 ms |

读数的时候有个细节值得注意：**登录（79 ms）比业务查询（8.0 ms）慢了一个数量级**。这是合理的——登录要做密码校验、生成并签发 JWT，而品牌列表只是一次简单的分页查询。所以看压测报告不能只看平均值，要按接口拆开看。

（登录耗时的具体构成我没有做代码级确认，这里只写到这个程度。）

## 几条比用例本身更重要的方法论

这是这个项目里我认为最该带走的部分。

**一、不写假数据。** 文档里有数字的地方，就必须是真跑出来的。跑不出来的项一律留 `〔待填：…〕`，绝不填一个"看起来差不多"的估算值。这条听起来是废话，但实际写文档时手最痒——一个漂亮的数字和一句"待填"摆在一起，前者太诱人了。

**二、`xfail` 是缺陷，不是失败。** 5 条用例用 `xfail(strict=True)` 标记，它们断言的是"系统应有的正确行为"。这样组织有两个好处：测试套件常绿（不会因为已知缺陷天天报红而被忽略），同时**一旦上游把 Bug 修了，这些用例会自动变成 `XPASS` 并失败**——等于免费得到一次"缺陷已修复，可以关单了"的提醒。

**三、诚实标注推断。** 结论只写到证据能支撑的范围，推断的地方明确写"这是推断"，没验证的地方就写"未做代码级确认"。把没验证的东西说成结论，短期看着漂亮，被追问一句就塌了。

**四、两套编号别混。** 用例编号（`A1` / `C7` / `F2d`）和缺陷编号（`F1`~`F8`）是两套独立体系，混用会让文档彻底失去可查性。这是我在整理文档时返工过的地方。

## 收获

这个项目最大的价值不是"测出了 8 个缺陷"，而是让我把接口测试从"会写用例"推进到了**"知道为什么这么写"**：

- 测试用例的价值不在于数量，而在于它背后对**业务约束**的理解程度；
- 断言必须分层，否则你测的是"接口没挂"，而不是"功能是对的"；
- 一个缺陷报告的质量，取决于你能不能把「现象 → 根因 → 影响 → 修复建议」讲成一条链，而不只是甩一个截图；
- 文档里那些"待填"和"说明这是推断"，才是让人信服的部分。
