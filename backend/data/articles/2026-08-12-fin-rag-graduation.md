## 为什么做这个题目

上市公司的年报平均有两三百页，充满专业术语、复杂表格和结构化信息。对投资者、分析师和监管部门来说，从海量年报里找出「某公司某年营收多少」「流动比率怎么算」这类答案，是一件既耗时又容易出错的事。

大模型很强大，但直接拿来回答金融文档问题有三个硬伤：

1. **幻觉问题**：模型会一本正经地编造不存在的数字，而金融场景里一个数字错了就是事故。
2. **时效性局限**：模型的知识停留在训练数据截止时刻，拿不到最新的财报。
3. **可追溯性缺失**：答案找不到出处，无法满足金融监管「谁回答、谁负责」的要求。

RAG（检索增强生成）正好指向这三个问题：先检索真实文档片段，再让模型基于片段作答。我的毕设就是把 RAG 用到金融文档上，核心目标就四个字：**准确、可溯源**。

## 第一阶：结构化解析

年报里最容易被普通切块方案毁掉的，就是**表格**——行列对应的关系一旦被扁平化成纯文本，数值就再也对不上号了。所以第一步解析的目标，是**保住结构**。

具体做法：

- 用 `PyMuPDF`（`fitz`）抽取 PDF 的文本和表格——`page.find_tables()` 直接拿到带坐标的表格结构，比从零手写解析稳得多。
- **表格转 JSON**：把二维表格转换成带表头、表尾、字段类型等元信息的结构化 JSON，而不是压成一行字。
- 处理两个经典难点：**跨页表格**按「页码关联 + 内容连续性检测」合并，**复杂表头**（多级表头、合并单元格）逐层展开。
- 从文本和表格里抽取「公司—指标—时间—数值」**四元组**（例如"安靠智电—营收—2019—8.05 亿"），为后面的知识图谱打底。
- 数值做**归一化**：中文数字转阿拉伯数字（"两亿七千五百万"→275000000），单位统一（万元 / 亿元 → 元）——金融文档里同一笔数有无数种写法，不归一化后面全对不上。
- 每个片段都挂上来源文档、页码、坐标等**溯源标记**——这是最后能出溯源报告的前提。

## 第二阶：混合知识库

不同类型的知识放进不同的仓库，各取所长：

| 数据形态 | 存储 | 作用 |
|---------|------|------|
| 非结构化文本 | FAISS 向量库 | 语义相似检索 |
| 结构化表格 | MongoDB | 精确匹配、跨表格关联 |
| 四元组关系 | Neo4j 知识图谱 | 多跳关系推理 |

### 文本向量库（FAISS）

用 `sentence-transformers` 加载 `bge-large-zh-v1.5`（1024 维）生成章节级文本块的语义向量，存入 FAISS。这里用的是一个容易被忽略的细节：向量在入库前先做了 **L2 归一化**，于是 `IndexFlatIP` 的内积就等于余弦相似度——既省了一次余弦计算，又让向量检索更快。

![图2-2 文本向量化及 FAISS 索引构建](/blog/fig2-2-vector-faiss.png)
*图2-2 文本向量化及 FAISS 索引构建：切块 → 编码 → 归一化 → 建索引*

### 表格库（MongoDB）

结构化表格存 MongoDB，每个文档带 `table_id`（文件名 + 页码 + 表格序号拼接，建**唯一索引**）、`source`（来源文档）、`page`（页码）、`headers`（表头）和 `data`（行数据），并按「公司名称 / 财年年份 / 指标类别」建**组合索引**，保证精确查询和跨表关联的速度。

![图4-3 MongoDB 表格库表结构](/blog/fig4-3-mongodb-schema.png)
*图4-3 MongoDB 表格库结构：table_id 唯一 + 多字段组合索引*

### 知识图谱（Neo4j）

四元组组装成图：Schema 里有 4 类节点（**公司 / 指标 / 年份 / 数值**）和 4 类关系（**拥有指标 / 属于年份 / 对应数值 / 属于年份**）。这样"某公司某年某个指标是多少"就变成图里的一条路径，多跳关系（"比较 A、B 两家公司的毛利率趋势"）可以直接在图里走。

![图2-5 知识图谱 Schema 结构](/blog/fig2-5-kg-schema.png)
*图2-5 知识图谱 Schema：公司—指标—年份—数值四类节点与关系*

入库用 `UNWIND` + `MERGE` 批量导入，每批 5000 条——单条 Cypher 逐条创建在几百万节点的量级下完全不可行，批量导入配合 MERGE 去重是必须的。

![图4-2 图谱构建流程](/blog/fig4-2-kg-build-flow.png)
*图4-2 图谱构建流程：四元组 → 节点/关系 → 批量入库*

这样，一个"公司间毛利率对比"的问题既能命中文本语义，又能通过图谱找到两家公司的关联关系，还能精确取到表格里的数字。

## 第三阶：混合检索与重排序

单路检索总是不稳，我做的是「元数据过滤 → 多路召回 → 加权融合 → 重排序」的四级流程：

1. **元数据过滤**：先按公司名称、财年、报表类型快速筛掉无关文档，把百万级候选缩到几千段。
2. **多路召回**：
   - **BM25 关键词检索**（`rank_bm25`）负责专业术语的精确匹配（比如「ROE」「流动比率」这种词）；
   - **FAISS 语义向量**负责语义相近的模糊匹配（"这家公司这两年赚得怎么样"这类说法）；
   - **知识图谱**负责精确数值（直接取出"公司—指标—年份—数值"四元组）。
3. **加权融合**：BM25 权重 0.4、向量权重 0.6 做分数融合；当查询里出现数字、百分号、"第 X 年"等信号时，自动切到 0.5 / 0.5，避免把精确数值类问题当成纯语义问题。
4. **重排序**：融合后的 Top-30 再交给 **BGE Reranker**（`bge-reranker-large` 交叉编码器）逐段重新打分，精排 Top-5 才交给大模型。

检索层还有三个增强手段：

- **查询扩展**：财务指标**同义词替换**（"营业成本"→"营业成本/营业总成本/主营业务成本"），以及**多年份问题拆分**（"对比 2019 和 2021 年"拆成两个查询）；
- **公司源过滤**：同一家公司的多份年报只保留对应财年的片段，防止"同名不同年份"互相污染；
- **知识图谱强制置顶**：图谱里命中的精确数值四元组直接注入结果前列，保证数值类问题不走偏。

## 第四阶：程序辅助生成（PAL）

数值计算是金融问答里最容易翻车的地方——让模型心算「2020 年营收 ÷ 2019 年营收」这种事，出错率很高。我的做法是**不让模型算，让代码算**。

### 意图分类

先用规则把用户问题分成三类，优先级是**计算类 → 对比类 → 事实类**：

- 命中「计算 / 除以 / 乘以 / 求和 / 平均 / 加权」等关键词 → 计算类；
- 命中「对比 / 比较 / vs」等 → 对比类；
- 其余 → 事实类。

用规则而不是模型，是因为它**零推理成本、完全可解释**，而且计算类必须排在最前面——不然"2020 年营收比 2019 年多百分之几"会被"多百分之几"误导成事实类。

### PAL：程序辅助推理

对计算类问题，引导大模型生成一段 **Python 代码**（比如"读取检索到的 2019/2020 营收，计算同比增长率"），丢进**安全沙箱执行**，用代码算出来而不是让模型口算。图 2-7 是完整的流程：

![图2-7 PAL 程序辅助推理流程](/blog/fig2-7-pal-flow.png)
*图2-7 PAL 完整流程：意图分类 → 生成代码 → 沙箱执行 → 数值校验*

**沙箱是安全与能力的平衡**：既要给模型写代码的能力，又不能让一句恶意的或越界的代码炸掉整个服务。我的 `safe_exec` 做了六层防护：

1. **静态关键词扫描**：先扫一遍，出现 `os` / `sys` / `subprocess` / `open` 等危险关键词直接拒绝；
2. **AST 白名单**：把代码解析成语法树，只放行 `赋值 / if / for / while / 表达式` 等安全语句，其他一律拦截；
3. **受限命名空间**：执行环境里只放检索到的数值事实，不暴露任何系统对象；
4. **子进程 + 超时**：在独立子进程里跑，2 秒超时强杀，死循环也拖不垮主服务；
5. **事实变量不可变**：检索到的数值只能被读取、不能被生成逻辑篡改——这是防止"模型算出一个漂亮的假数字"的关键；
6. **返回值约束**：只接受能安全序列化的数值结果。

再加上**中文数字转 float**（"两亿七千五百万"→ 2.75e8）和**单位归一化**（万元 / 亿元 → 元），保证进沙箱的输入是干净的数字。

### 多阶段校验与溯源

- **事实一致性检测**：生成片段 vs 检索片段比对，不吻合就重生成或拒答；
- **逻辑连贯性检测**：检查回答是否自洽；
- **数值准确性检测**：计算结果复核，多算一步验证；
- **全链路溯源**：每个答案标注来源文档、页码、段落位置、检索推理路径，输出一份溯源报告——这正是金融合规最看重的东西。

## 一条查询的完整旅程

拿「计算安靠智电 2019 年的流动比率」来走一遍全流程：

1. **元数据过滤**：先按"安靠智电 + 2019 + 资产负债表"锁定年报中的对应章节，把十万页候选缩到几百段。
2. **三路召回**：BM25 命中"流动比率"这个术语，密集向量命中"流动资产 / 流动负债"相关语义段落，知识图谱直接取出 2019 年流动资产与流动负债的**原始数值**。
3. **加权融合 + 重排**：BGE Reranker 把最相关的段落排到前面，Top-5 进生成器。
4. **PAL 生成**：意图分类器判定这是数值计算型问题 → 大模型生成代码 `流动比率 = 流动资产 / 流动负债` → 沙箱执行拿到准确结果。
5. **校验 + 溯源**：数值复核通过，答案带上"来源：xx 年报第 xx 页 资产负债表"的引用，用户一点就能看到原文。

整个过程用户拿到的不只是一个数字，还有完整的证据链。

## 工程细节：增量解析与热更新

毕业设计要处理的数据规模让我意识到，**全量重建是奢侈品**：20 份年报本地开发没问题，云端上线是 4346 份年报、数百万片段，每次新增都全量重建索引根本不可行。所以系统支持：

- **文档上传解析**：用户在界面传一份 PDF，系统走「上传 → 解析 → 入库」全流程。图 3-6：

## 评测：面向问题的评测

我构建了 100+ 条金融问答对（事实 / 计算 / 对比三类），从**意图识别、检索命中、生成质量、幻觉率、计算准确率**等多个维度做评测，并设计了两组消融实验（移除知识图谱通道、移除重排序模块）来验证各组件的贡献。

评测的意义不在于跑出一个好看的数字，而在于**暴露问题**。它让我看清了这类系统最薄弱的两个环节：

1. **跨财年检索错误**：问"某公司 2021 年营业成本"，检索回来的却是同公司 **2020 年年报**的片段——同名公司、不同财年，是幻觉的主要来源。这直接推动了「公司源过滤 + 图谱强制置顶」这两个机制的上线。
2. **计算输入不完整**：计算类问题有时算错，不是因为 PAL 代码错，而是**检索阶段没把需要的全部数值事实取回来**——输入错了，代码再对也没用。这让我把优化重心从"调提示词"转移到"调检索"。

这两条结论的价值，比任何单点指标都重要——它们决定了后续优化的方向。

## 源码复盘：设计与实现的心得

毕业设计做完后回看源码，有几条心得想记下来。

### 1. 开题是理想，落地是现实

开题报告里写的方案，和真正写出来的代码有几处明显的差异，每一处都是"用脚投票"：

| 开题设想 | 实际落地 | 为什么 |
|---------|---------|--------|
| vLLM 本地部署大模型 | DeepSeek API + 本地小模型兜底 | 本地大模型显存、部署、稳定性成本太高，API 开箱即用；本地兜底保住"数据不出内网"的底线 |
| pdfplumber + Table Transformer 解析表格 | PyMuPDF（`fitz.find_tables()`） | PyMuPDF 的表格检测直接可用、坐标齐全，够用就够，不叠复杂度 |
| FAISS IVF_FLAT 索引 | `IndexFlatIP` 内积索引 | 数据量级下内积暴力检索更快更简单；向量归一化后内积即余弦，没必要上 IVF |

教训：**架构设计先按最简单的做，遇到瓶颈再升级**，而不是一开始就把所有 fancy 的东西堆上。

### 2. 规则式意图分类：够用就好

意图分类没有用模型，而是正则 + 优先级。三行规则（计算优先 → 对比 → 事实）就能覆盖绝大多数金融问答，还零推理成本、完全可解释。**能用规则解决的，不要动用模型**——这是这套系统里性价比最高的一处设计。

### 3. PAL 沙箱：安全与能力的平衡

给大模型写代码的权力，等于把执行权交给了一个不可控对象。六层沙箱里我认为最值钱的两条是：

- **AST 白名单**：从语法层面就只允许安全语句，而不是靠关键词黑名单（黑名单永远列不全）；
- **事实变量不可变**：检索到的数值只能读不能改——这一条直接堵住了"模型为了凑答案而篡改数据"的路。

### 4. 中文数字和单位，是金融数据的魔鬼

"两亿七千五百万""2.75 亿""27500 万元"说的是同一笔钱。不做**中文数字转 float** 和**单位归一化**，PAL 算出来的一定是错的——而且错得很难察觉。金融数据清洗，先把数字"标准化"这一关过了，后面才谈得上准确。

### 5. 检索层和生成层之间的缝隙，是最值得打磨的地方

评测暴露的两个问题（跨财年检索、计算输入不完整）有一个共同点：**问题出在"检索层给的东西不够好"，而不是"生成层不够聪明"**。调模型、调提示词只能微调，真正决定这类系统上限的是检索质量。这也解释了为什么我把最多的时间花在检索的工程细节上——公司源过滤、图谱置顶、同义词扩展，每一处都是把"检索结果"往正确方向推一把。

### 6. 规模会改变一切假设

本地 20 份年报跑通的东西，到云端 4346 份年报、几百万片段时，很多"没问题"都变成"不可行"：全量重建不可行 → 做增量解析；单条写 Neo4j 不可行 → 做 UNWIND 批量导入；阻塞式解析不可行 → 做双队列 + 热更新。**设计时就要问自己：这个方案在 100 倍规模下还成立吗？**

### 7. 开源组件的坑，绕比改源码划算

Gradio 3 的 Markdown 代码渲染组件有个 DOM 竞态：返回内容里带特殊字符的代码块会导致页面渲染崩溃。最后用 `html.escape` 转义就绕过去了。**遇到框架级 bug，先找 workaround，别急着改源码**——改框架源码意味着你要维护一个 fork。

## 难点与收获

这个题目最大的难点不是"接个大模型"，而是**让结构化数据和生成式 AI 协同**：

- 表格必须保结构地进知识库，否则数值问答全崩；
- 检索不能只靠一路，术语精确匹配、语义匹配和精确数值要融合；
- 数值计算必须交给代码而不是模型心算；
- 每个答案都要能指回原文，这是金融场景的底线。

另外有意思的是，它和这个博客的 AI 问答机器人是**同一种技术**——都是 RAG。博客里那篇《给个人博客接上 DeepSeek + RAG 智能问答》是轻量版（ChromaDB 单库），毕设则把同样的思路做成了多知识源、可溯源、带计算能力的完整形态。从两三百页的年报到两分钟的实时问答，正是检索增强想解决的问题。
