## 被测的 App 不是我写的

先说清楚：被测对象是 [@wj576038874](https://github.com/wj576038874/WanAndroidCompose) 的开源项目 **WanAndroidCompose**——一个用 Kotlin + Jetpack Compose 写的「玩安卓」客户端。

我拿它当测试对象，**没有改过它任何一行业务代码**。它没挂 LICENSE 文件，按著作权法默认就是「保留所有权利」，所以我也不好替别人再分发一遍——仓库里没有它的源码，只有我写的测试脚本、报告和证据。

这种"只测别人、不碰源码"的定位其实挺接近真实工作的：你入职一家公司，被测系统本来就不是你写的。

## 七个环节，各自测出什么

| 环节 | 做法 | 结果 |
|---|---|---|
| 功能 | 手动设计 5 条主路径用例（列表加载 / 加载更多 / 进详情 / Tab 切换 / 返回键） | **5/5 通过**，挖出 1 个 Bug |
| UI 自动化 | uiautomator2 + adb，冷启动自动点开文章 | 通过 |
| 稳定性 | Monkey 300 事件，`-s 42` 固定种子，throttle 200 ms | **无崩溃、无 ANR** |
| 抓包 | mitmproxy 代理抓包，梳理核心接口 | 文章列表、Banner |
| 接口自动化 | pytest + 三层断言 | **2/2 通过**（1.31 s） |
| 性能 | JMeter 非 GUI，20 并发压列表接口 | 平均 **1958 ms**，错误率 **0%** |
| 弱网 | 4 参数 × 4 观察点，实测排查 | 定位 3 层干扰，**量化表没跑成** |

七项里六项有量化结论，最后一项我承认没做成——这个放到后面单独说，因为它比成功的那几项更有意思。

## 几个真踩到的坑

### Monkey 为什么要用固定种子

```bash
adb shell monkey -p com.wanandroid.compose --throttle 200 \
  --pct-touch 60 --pct-motion 20 --pct-nav 0 --pct-appswitch 0 -s 42 300
```

`-s 42` 是**固定随机种子**。它意味着这次跑的 300 个事件序列是确定的——真崩了，同一条命令能把同一个序列复现出来。

这一条我认为是 Monkey 测试里最容易被忽略、但最重要的参数：**复现得出来，才谈得上定位**。随机跑 300 个事件谁都会，跑出崩溃之后能再跑出一次同样的崩溃，才是能力。

`--throttle 200` 是事件间隔 200 ms（模拟真人操作节奏，太快容易把系统压出假崩），`--pct-touch 60 --pct-motion 20` 让触摸和滑动占大头，比纯随机乱点更接近真实使用。

跑完的结果：无崩溃、无 ANR。

### UI 自动化的三个坑

写一个"冷启动 App → 自动点开一篇文章 → 截图"的脚本，听起来十分钟的事，实际踩了三个坑：

**坑一：双启动入口。** debug 包带了 leakcanary，于是它有两个启动 Activity。不显式指定 `.MainActivity` 的话，脚本会偶发落到错误界面。**debug 包的构建配置会改变被测对象的行为**——这一点在用测试包做自动化时必须意识到。

**坑二：标题没法写死。** 首页拉的是真实数据，每次刷新内容都不一样，脚本里写死一个文章标题必然失败。改成**从当前 UI 树里动态挑「内容区最上面的长文本」**当点击目标——让脚本去适应界面，而不是让界面来适应脚本。

**坑三：点击坐标会打偏。** 在这台 Android 17 模拟器上，uiautomator2 的 `click()` 会点偏（结果点进了系统设置）。但排查后发现 u2 读 UI 树和元素 `bounds` 是准的。于是改成 **u2 负责读坐标、`adb shell input tap` 负责执行点击**，问题解决。

第三个坑挺典型的：工具出问题时，不一定要换工具，**把它的能力拆开用**往往就够了。

### 一个 Bug 的定位过程

现象：个人信息页 → About → 内嵌网页里文字挤成一团，完全没法读。

这是 UI 问题，但**难的不是发现，是判断"这是谁的锅"**。App 里可能有好几种界面：原生 Compose 页面、WebView、系统浏览器。修法完全不同。

定位过程：

1. 用 `dumpsys window` 看当前前台窗口是谁；
2. 再用 UI 树确认一遍；
3. 结果前台是 `com.android.chrome` 的 `CustomTabActivity`。

**结论：这个页面是 App 用内嵌浏览器打开的外部网页，不是原生界面。** 问题出在那个网页自身没有做移动端适配，跟 App 的原生代码没关系。

如果不查这一步，直接按"App 页面错乱"提给开发，大概率会被打回来——或者更糟，被当成 App 的 Bug 修半天。

缺陷记录按 Bug 五要素写（现象、预期、实际、复现步骤、环境）。这个缺陷当时只留了文字没单独截图，所以这里也不放图——没有证据就不装。

### 接口断言为什么分三层

抓包梳理出的两个核心接口：

| 接口 | 用途 | 成功判定 |
|---|---|---|
| `GET /article/list/{页}/json` | 首页文章列表 | `errorCode == 0` 且 `data.datas[]` 非空 |
| `GET /banner/json` | 首页 Banner | `errorCode == 0` 且 `data[]` 非空 |

两条用例都做**三层断言**：

```
第 ① 层  网络层：HTTP 200
第 ② 层  业务层：errorCode == 0
第 ③ 层  数据层：data 里的数组非空
```

这么分不是为了好看，是为了**失败时能一眼看出卡在哪一层**，而不是笼统报一句"接口挂了"。网络层挂是环境问题，业务层挂是服务端逻辑问题，数据层挂是数据问题——三种情况的处理人都不一样。

**抓包这块我要说清楚范围**：App 自己的 HTTPS 流量要抓到明文，得把代理证书装进系统证书区（需要 root，属进阶操作），这次没做。我实际是抓模拟器**浏览器**访问 wanandroid 同一套后端的流量来确认接口的。接口确实和应用依赖的是同一套，但这**不等于直接解了 App 的包**——这个区别我不想含糊过去。

## 性能：20 并发下的数字

![JMeter 性能仪表盘](/blog/app-test-jmeter-dashboard.png)

| 平均 | 中位数 | 90% 分位 | 最大 | 吞吐 | 错误率 |
|---|---|---|---|---|---|
| 1958.45 ms | 1939.50 ms | 2510.30 ms | 2552 ms | 7.78 req/s | 0.00% |

数字取自 JMeter 自己输出的 `statistics.json`，可以复核。

这里有个刻意的选择：**只压 20 并发**。因为压的是 wanandroid.com 的**线上公共接口**，不是我的环境——给别人的线上服务上压力，测试做得再漂亮也是给别人添堵。所以这次压测的目标不是"找出性能上限"，而是"把压测流程完整走一遍并拿到可信数据"。

平均 1958 ms 这个数字偏慢，但它是**公网 + 第三方服务 + 模拟器链路**的综合结果，不能直接当成 App 的性能结论。这点必须说清楚。

## 我没做成的那部分

弱网测试。方法论我掌握了，也真去排查了，但**「限速之后加载变慢」的量化对比表没跑成**——模拟器的网络整形对这个 App 的流量不生效。

我按 4 个参数设计（带宽、延迟、丢包、抖动），固定 4 个观察点（loading 提示、超时错误、崩溃错乱、网络恢复），实测排查后定位到 3 层干扰。原因我查清楚写进观察记录了，但**没做成的就是没做成**。

不过这一轮也不是白跑，有个意外发现挺有价值：

![彻底断网冷启动，列表居然还在](/blog/app-test-offline-cache.png)

**彻底断网之后冷启动，列表居然还能显示出来**——说明这个 App 做了本地缓存，弱网/断网下并不是白屏。这本身是个值得记录的行为（缓存策略的证据），也提醒我：弱网测试的观察点不该只有"变慢了没有"，"降级表现是否合理"同样重要。

把失败的部分老实写进报告，比把它藏起来更有用——因为"为什么没做成"这个信息，对下一个要接手的人是有价值的。

## 为了让它编译起来，我改了两处

上游默认从 Google 和 services.gradle.org 拉依赖，国内网络拉不动。我改了两处**构建配置**，没碰任何业务代码：

- `gradle/wrapper/gradle-wrapper.properties`：Gradle 分发包换成腾讯镜像；
- `settings.gradle.kts`：在 `pluginManagement` 和 `dependencyResolutionManagement` 里加了阿里云 Maven 源。

这类改动我会在仓库里明确写出来——**"我改了构建配置"和"我改了被测代码"是完全不同的两件事**，在测试项目里必须分得清清楚楚，否则测试结论的可信度就没了。

## 收获

这个项目让我第一次把 App 测试的**全链路**走通了一遍，而不只是会跑某一个工具：

- **先手动摸一遍，再考虑自动化。** 手动用例帮你想清楚主路径在哪、什么算"对"，自动化只是把它固化下来。跳过手动直接写脚本，写出来的往往是"能跑但没测什么"的东西。
- **可复现是测试的基本盘。** Monkey 固定种子、脚本不写死数据、用例可重复执行——这些都是同一个原则的不同侧面。
- **每条结论都要能追到证据。** 报告里的每个数字都指向一个原始文件（日志、jtl、截图、HTML 报告），这让人没法反驳，也让我自己不敢乱写。
- **诚实比好看重要。** 没跑成的弱网量化表、没抓到的 App HTTPS 明文、没截图的缺陷——这些我都写进文档里了。一份承认了三处局限的报告，比一份处处完美的报告可信得多。
- **测试的边界是版权。** 被测对象是别人的，我能做的是测试、是记录、是引用，而不是把它的源码和资产打包进自己的仓库。
